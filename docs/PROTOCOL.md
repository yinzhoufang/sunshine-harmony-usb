# USB 媒体隧道协议

当前实现保留三字节帧头，使用两条双向 TCP 隧道。HDC 只负责长连接端口转发；数据报不会逐包执行命令行。

## 通道与连接

| 通道 | 含义 | TCP 隧道 |
|---|---|---|
| 0 | 视频 | 47997 |
| 1 | 控制 | 47996 |
| 2 | 音频 | 47996 |

帧格式：`channel:u8` + `length:u16（大端）` + `payload:length bytes`。每帧承载一个 UDP 数据报，不改写其载荷。TCP 接收端必须处理半包和粘包，断线后丢弃旧连接残留的半帧。

TCP 应用控制、配对和 RTSP 使用独立的透明 TCP 代理，不使用上述媒体帧头。TCP 代理必须在 upstream 连接成功前缓存客户端数据，连好后再补发。

## 端口

USB 模式下 Sunshine 端口基准为 48989。中继占用标准媒体端口，与 Sunshine 的偏移端口通信。

| 用途 | 平板侧 / 中继端口 | PC Sunshine 端口 |
|---|---:|---:|
| HTTP | 47989 | 48989 |
| HTTPS 配对 | 47984 | 48984 |
| RTSP | 48010 | 49010 |
| 视频 UDP | 47998 | 48998 |
| 控制 UDP | 47999 | 48999 |
| 音频 UDP | 48000 | 49000 |

媒体本身通过 47997 / 47996 隧道传输，表中的 UDP 端口由桥和中继对接。为兼容客户端从响应中读到的偏移端口，脚本另建立 48984→48984、48989→48989 的 TCP 映射。

桥在平板本机 `127.0.0.2` 接受 Moonlight 连接。UDP 下行目的端口必须根据对应通道客户端的真实上行来源学习，不能把 ENet 来源端口当成固定值。

## 调度与队列

平板媒体面由 C++ 工作线程处理，输入上行优先，每处理一小批视频数据报后检查控制。PC 保留 2 MiB 队列上限；不要仅为追求低延迟随意压缩到 256 KiB，也不要恢复依赖 ArkTS Promise 完成回调计数的下行限流。

当前机制减少排队对输入的影响，但两条 TCP 隧道仍共享 USB / HDC 和系统调度，不保证完全消除队头阻塞或调度抖动。
